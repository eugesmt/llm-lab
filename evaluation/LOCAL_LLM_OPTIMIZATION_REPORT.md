# Оптимизация локальной LLM для SRE-диагностики

Дата прогона: 11 октября 2026 года.

## Задача

Локальная модель выполняет безопасную первичную диагностику SRE-инцидентов:
по небольшому снимку метрик называет вероятное узкое место и предлагает только
диагностические проверки. Изменение системы, удаление и перезапуск намеренно
исключены — маленькая модель недостаточно надёжна для автономного remediation.

Финальная модель: `llm-lab-sre:latest`, созданная из `qwen2.5:3b` (Qwen2.5
3B Instruct). Это instruct-модель без отдельного reasoning/thinking-режима:
ответ сразу содержит финальный текст, поэтому скрытые рассуждения не нужно
отключать параметром.

## Конфигурации

| Параметр | До (baseline) | После (optimized) |
|---|---:|---:|
| Base model | Qwen2.5 3B Instruct | та же |
| Temperature | default Ollama | 0.1 |
| Max tokens | без лимита в старом адаптере; safety cap 512 в тесте | 192 |
| Context window | default Ollama | явно 4096 |
| Prompt | только вопрос пользователя | SRE system prompt, два обязательных блока |
| Допустимый ответ | свободный | только `Диагноз` и `Проверки` |

В prompt добавлены правила согласованности метрик: высокий `iowait` при низком
CPU трактуется как ожидание I/O, `IUse=100%` — как исчерпание inode, а долгое
ожидание соединения при быстрых SQL — как узкое место пула. Разрушительные
действия запрещены, и финальная серия не содержит команд удаления или изменения
системы.

## Методика

Пять фиксированных сценариев находятся в `local_llm_cases.json`: disk I/O, inode,
пул PostgreSQL, DNS и memory pressure. Обе конфигурации выполнялись
последовательно на одном локальном Ollama и одном оборудовании.

Открытая рубрика качества (0–10): 8 баллов за ожидаемые группы фактов, 1 балл за
оба обязательных заголовка и 1 за непустой ответ до 1200 символов. Native Ollama
API возвращает wall time, токены, скорость декодирования и объём загруженной
модели. Полные запросы, ответы и числа сохранены в `local_llm_results.json`.

## Результаты

| Метрика, среднее по 5 кейсам | До | После | Изменение |
|---|---:|---:|---:|
| Качество, 0–10 | 4.60 | 5.20 | **+0.60 (+13%)** |
| Latency, среднее | 5.85 с | 0.79 с | **−86.5% (в 7.4 раза быстрее)** |
| Latency, медиана | 5.82 с | 0.83 с | **−85.8% (в 7.0 раз быстрее)** |
| Сгенерировано токенов | 512.0 | 45.4 | **−91.1%** |
| Скорость декодирования | 93.00 tok/s | 89.49 tok/s | сопоставима по порядку |
| Память модели по Ollama | 2.16 ГБ | 2.16 ГБ | без изменений |
| Фактический context Ollama | 4096 | 4096 | после явно зафиксирован |

Ускорение появилось не из-за роста tokens/s, а за счёт короткого шаблона и
ограничения генерации. Все пять optimized-ответов остались короткими и начинались
с требуемого формата; маленькая Qwen2.5 иногда выбирает неверную категорию, поэтому
ответ перед запуском команд проверяет оператор.

Smoke-проверка через UI на сценарии disk I/O дала 4313 мс при первой загрузке и
1069 мс после прогрева. В обоих случаях модель сгенерировала 56 токенов, а поле
reasoning осталось пустым.

## Квантование и ресурсы

Профиль использует локальную квантованную сборку Qwen2.5 3B (формат Ollama,
размер зависит от тега и версии Ollama). Для 3B FP16 только веса потребовали бы
ориентировочно 6 ГБ, поэтому Q4-профиль подходит для машины с 8 ГБ RAM.

Уменьшения RAM в данном прогоне нет, потому что baseline Ollama также фактически
запустил с окном 4096. Явная фиксация окна всё равно важна: профиль не сможет
неожиданно развернуть заявленный моделью максимум 32768 на длинном запросе.

## Воспроизведение

```bash
ollama create llm-lab-sre:latest -f ollama/Modelfile.sre
uv run python evaluation/run_local_optimization.py
```

Для повторного прогона одного профиля с сохранением второго:

```bash
uv run python evaluation/run_local_optimization.py --only optimized
```

## Ограничения

- По одному прогону каждого кейса: для статистической уверенности нужны хотя бы
  3–5 повторов.
- Рубрика лексическая и не заменяет экспертную оценку; поэтому выполнена ручная
  проверка безопасности.
- Первый baseline-запрос включал холодную загрузку модели, но вывод об ускорении
  сохраняется и по медиане.
- Качество 5.2/10 означает, что профиль подходит только для подсказки оператору,
  но не для автономного принятия решений. Команды перед запуском должен проверять
  SRE.

## Вывод

Получен воспроизводимый локальный профиль под узкий кейс. Низкая температура,
лимит 192 токена, окно 4096 и предметный prompt повысили измеряемое качество и
снизили медианную задержку в 7 раз при том же объёме Q4_K_M модели. Qwen2.5 3B
работает без скрытого режима thinking, а область ответственности модели сужена
до безопасной диагностики без самостоятельного remediation.
